## Concurrency and protected features (read first)

Several Claude sessions work on this repository at the same time (daily content session, SEO, design, security / CRM). The rules below bind every session. The build guard enforces them: a commit that drops a protected feature FAILS the Vercel build and production keeps serving the last good deployment.

1. **Always start by fetching and rebasing onto `origin/main`** (`git fetch origin main && git rebase origin/main`), and rebase again immediately before pushing.
2. **Publish only through `bash scripts/publish.sh`.** It fetches, refuses uncommitted changes, rebases (stops on conflict and lists the files), runs `scripts/inject-gtm.js`, `scripts/guard.js`, `tools/test-lead.js` (and the attribution browser test when Playwright exists), then pushes without force and retries up to 3 times if another session pushed first. Never `git push --force`, `--force-with-lease`, or `git reset --hard` over unpushed work.
3. **Change only the files your task needs, with minimal edits.** Never regenerate or overwrite a whole shared file (`index.html`, `api/lead.js`, `aim-track.js`, `aim-magnet.js`, `frontend.js`, `privacy-policy.html`, `vercel.json`, `robots.txt`, `sitemap.xml`, `llms*.txt`, `blogs/index.html`, CSS files) from a stale template or an old copy. When creating a blog post, copy the shell from the NEWEST published post on `origin/main`, not from memory or an older post.
4. **Security, privacy, tracking and CRM features are PROTECTED**: IP and location capture, origin check and rate limiting, abuse records, UTM attribution, GTM and the event script, privacy-policy wording, the decoy login handling, redirects, headers, author and schema blocks. They have priority over content or design changes and must never be removed, weakened or bypassed. If a requested change would conflict, keep the protected feature and tell the owner.
5. **Adding a protected feature?** In the same commit add its invariant to `INVARIANTS` in `scripts/guard.js` (id, title, owner-facing `why`, `check`) plus a test, raise `MIN_LEAD_TESTS` if you added lead tests, and update the list below. The guard is what stops later sessions from dropping it.
6. **If the guard fails, fix the cause.** Never disable or loosen a check, and never set `GUARD_SOFT` to get a deploy through. Only the owner may set `GUARD_SOFT=1` in Vercel (Settings > Environment Variables) in an emergency when the guard blocks something legitimate: the guard then prints the same violations as warnings and exits 0. Remove the variable afterwards.
7. **Never redeploy an older deployment from Vercel** (it rolls the site back and drops newer features). To roll forward, push a new commit.
8. **After pushing**, wait for the Vercel production deployment of YOUR commit to be READY, confirm `aiinmarketing.in` and `www.aiinmarketing.in` are aliased to it, and run `node scripts/live-check.js` (must print `LIVE CHECK OK`). If the deployment ERRORs because of the guard, read the build log and fix forward.
9. **If a protected feature is already missing on main**, restore it from git history (`git log -S'<feature string>' -- <file>`) in a new commit, via `publish.sh`, and tell the owner.
10. **Content session checklist** before publishing a post: rebase, `bash scripts/publish.sh`, confirm the guard passes (it checks the author block, byline, schema, SEO lengths, Sources section, sitemap, `blogs/index.html`, `llms.txt`, author pages, GTM, price and guarantee wording). New posts need a "Sources" section (`<h2 id="sources">`); only the nine posts listed in `NO_SOURCES_GRANDFATHERED` in `scripts/guard.js` are exempt.

Protected invariants (each is an entry in `INVARIANTS` in `scripts/guard.js`; run `node scripts/guard.js`): `lead-endpoint-source` (origin allow-list, rate limit, repeat suppression, abuse records in Unqualified with IP + geo + UTM in the title, IP from x-real-ip then x-forwarded-for, Vercel geo headers, failure task, IST time, friendly form names, AbortController timeout, key only from `process.env`); `lead-tests` (`tools/test-lead.js` passes, at least `MIN_LEAD_TESTS` checks); `gtm-and-track-on-every-page` (GTM once as loader and noscript, old container nowhere, one `aim-track.js` at the current `TRACK_VER`, UTF-8, one canonical); `attribution-script` (UTM, click id, referrer, first/last touch storage, capture-phase submit listener, dataLayer events, forms still posting to `/wp-admin/admin-ajax.php`); `privacy-policy` (IP address, approximate location, Clarity, Google Analytics, Tag Manager, Heffl, campaign sentence, no-sale sentence, effective date); `vercel-config` (redirects, decoy-login and form rewrites, headers, `buildCommand` = inject-gtm then guard, `outputDirectory`); `robots-sitemap-login` (robots groups, sitemap lists exactly the public pages, no wp-login in sitemap or links, noindex on the decoy login); `blog-posts` (both authors, one authors block, Article + FAQPage JSON-LD, title/description lengths, Sources, magnet form hidden fields, listed in sitemap, blog index, `llms.txt` and both author pages; author pages with ProfilePage); `content-consistency` (only Rs 5,999, 7-day money-back wording, "Adsmentor" spelling, no placeholders); `secret-hygiene` (no keys or tokens, no tracked `.env`).

Tools: `node scripts/guard.js` (the build guard, runs in the Vercel build right after `inject-gtm`, no network, about 2 s), `node scripts/guard-selftest.js` (copies the repo and proves the guard fails after 12 kinds of regression; run it after changing `guard.js`), `bash scripts/publish.sh` (the only push route), `node scripts/live-check.js [baseUrl]` (post-deploy check of the live site, creates no leads).

### Recovery: something was overwritten

1. Find when it disappeared: `git log -S'<feature string>' --oneline -- <file>` (the last commit that touched the string either added or removed it; `git show <sha> -- <file>` shows which).
2. Restore only that section in a NEW commit on top of current main (`git show <good-sha>:<file>` to read the old text; edit the current file in place, do not overwrite it with the old copy). Never force-push or reset.
3. Run `bash scripts/publish.sh`, wait for the production deployment to be READY and aliased, then `node scripts/live-check.js`.
4. Tell the owner what was lost and when. If the guard did not catch it, add an invariant for it (rule 5).

## Lead capture: Heffl CRM

Every valid form submission (`/wp-admin/admin-ajax.php` -> `api/lead.js`) is created as a lead in Heffl when `HEFFL_API_KEY` is set. Without the key the function only logs (or forwards to `LEAD_WEBHOOK_URL`), so deploying before the key exists is safe. The key is never in the repo, never logged and never sent anywhere except the `x-api-key` header to `api.heffl.com`.

Environment variables (Vercel > Settings > Environment Variables):

| Variable | Required | Purpose |
| --- | --- | --- |
| `HEFFL_API_KEY` | yes (Production and Preview, mark Sensitive) | Heffl API key |
| `HEFFL_LEAD_SOURCE_NAME` | no, default `Website` | Heffl lead source, found by name |
| `HEFFL_LEAD_STAGE_NAME` | no, default `New` | Heffl lead stage, found by name |
| `HEFFL_USE_CUSTOM_FIELDS` | no, default off | Set to `true` only after creating ALL the lead custom fields listed under "Heffl columns" below |
| `LEAD_WEBHOOK_URL` | no | Fallback: receives leads Heffl could not store (Zapier, Make, Apps Script) |

How it works:

- Calls used (Heffl docs, checked 2026-11-03): `POST https://api.heffl.com/api/v1/leads` (name, mobile `+91<10 digits>`, email, sourceId, stageId), `GET /api/v1/leads/sources` and `GET /api/v1/leads/stages` (ids looked up by name, cached 1 h per warm instance; if the lookup fails the lead is created without them and Heffl uses its defaults), `POST /api/v2/tasks` (v2 is Beta). Rate limit 60 requests/min per key.
- Context the lead create call cannot hold (current situation = `form_fields[stage]`, form source, page URL without query, utm_* from the referer):
  - Default: a follow-up task linked to the lead (`entity: "leads"`, `entityId: "ld_..."`), type call, priority MEDIUM, due in 1 day, title `Follow up: <name> (<situation>, via <form source>)`, full context in the description.
  - Better, once the owner creates these Heffl custom fields (Settings > Custom fields, for leads) with exactly these labels, then sets `HEFFL_USE_CUSTOM_FIELDS=true`: `Current situation`, `Form source`, `Page URL`, `Campaign UTM`. The API keys are derived from the label (`cf_current_situation`, `cf_form_source`, `cf_page_url`, `cf_campaign_utm`; lowercase, spaces to underscores). Do not use a `/` in a label. If Heffl rejects the fields or does not echo them back, the function falls back to the task automatically.
  - Optional in Heffl itself: a "Lead Created" automation with a "Create Task" action (then the task from the API duplicates it; ask for the API task to be switched off if you do).
- The visitor never waits more than about 6 s for Heffl and never sees a Heffl error. On failure the function still answers success, logs one JSON line `{"event":"lead_crm_failed",...,"lead":{...}}` (personal data: Vercel runtime logs only) and posts the lead to `LEAD_WEBHOOK_URL` if set. 401/403 logs `check HEFFL_API_KEY permissions`; 429 is retried once if Heffl says to wait under 2 s; a duplicate contact (409 or a "duplicate" validation error, Heffl allows no second lead with the same phone/email) logs `duplicate_lead` and is NOT dropped: the person is stored again without contact fields, title `Repeat enquiry (contact already in Heffl): <email> <mobile>`, stage New, with the normal follow-up task (its text starts with `Repeat enquiry:` and the typed mobile/email).
- Abuse protection: Origin/Referer must be aiinmarketing.in or www.aiinmarketing.in (localhost only outside production); at most 5 submissions per IP per 10 minutes (best effort, in memory per instance); the same email+phone within 60 s is acknowledged but not sent again.
- Failure task: when Heffl is reachable but rejects the lead (4xx other than 401/403/429, e.g. validation), the function creates one Heffl task (`POST /api/v2/tasks`) titled `Lead capture failed: <name>, <mobile>, <friendly form>` (type todo, priority HIGH, due today, no lead link; description holds email and all context) so the team adds it by hand. If Heffl is unreachable (timeout/network), returns 401/403/429/5xx, or the task call fails too, the old fallback applies: `lead_crm_failed` log line plus `LEAD_WEBHOOK_URL`. When the task was created, the log line is `lead_failure_task_created` instead and the webhook is not called.
- Abuse records: a submission that passes basic validity (name >= 2 chars, valid Indian mobile, valid email) but is flagged is created as a Heffl lead in the `Unqualified` stage (looked up by name, cached like source/stage; never `New`) with the type at the START of the lead `title`: `ABUSE: <type> | IP <ip>, <city>, <region>, <country> | <friendly form>`. Plus one LOW-priority task linked to the abuse lead (`ABUSE: <type> - <name>`) holding the typed mobile and email, IP, location, form, situation, page and campaign (the lead record itself has no place for them, and Heffl leaves its contact fields empty when the contact is a duplicate). Types: `invalid_input` (400), `same_ip_multiple` (200, see below), `bad_origin` (response 400), `rate_limit` (429), `repeat_within_60s` (200 success), `bot_user_agent` (200 success; User-Agent matches HeadlessChrome, curl, python-requests, Go-http-client, node-fetch/undici/axios, wget, okhttp, scrapy, crawler/bot/spider etc.; a missing User-Agent is not flagged; the Playwright/mock QA runs never reach Heffl). No honeypot field exists, so there is no `honeypot` type. At most 20 abuse records per hour per warm instance (beyond that an `abuse_record_skipped` log line plus the full record to the log and `LEAD_WEBHOOK_URL`); requests with nothing typed create nothing (see NO DATA IS LOST below). Heffl rejects duplicate contacts, so if the abuse lead is a duplicate it is retried once without email/mobile, with `<email> <mobile>` in the title. If the `Unqualified` stage does not exist in Heffl nothing is created (create the stage). User-facing responses are never changed by abuse handling.
- IP and location (server side only, never in any response): IP = `x-real-ip`, else the first `x-forwarded-for` entry (trimmed, must be a valid IPv4/IPv6 of at most 45 chars, else ignored), else the socket address; the same IP drives the rate limit. Location = `x-vercel-ip-country` (2 letters), `x-vercel-ip-country-region`, `x-vercel-ip-city` (URL-decoded). Recorded: in the follow-up task text (`IP address`, `Approximate location`) and the failure task; in Heffl custom fields when `HEFFL_USE_CUSTOM_FIELDS=true` (add four more lead custom fields: `IP address`, `Country`, `Region`, `City` -> `cf_ip_address`, `cf_country`, `cf_region`, `cf_city`; if missing, Heffl rejects the create and the function falls back to the task); in the abuse title; and in the logs (`lead_crm_failed`, `abuse_flagged`, `lead_failure_task_created` carry `ip`, `country`, `region`, `city`, `abuse`).
- Heffl columns (owner creates them in Heffl: Settings > Custom fields > for Leads, labels EXACTLY as below, then sets `HEFFL_USE_CUSTOM_FIELDS=true` in Vercel and redeploys; the API cannot create columns): `Current situation`, `Form`, `Form source`, `Page URL`, `Campaign UTM`, `IP address`, `Country`, `Region`, `City`, `Abuse type` (keys `cf_current_situation`, `cf_form`, `cf_form_source`, `cf_page_url`, `cf_campaign_utm`, `cf_ip_address`, `cf_country`, `cf_region`, `cf_city`, `cf_abuse_type`). `Form` is the friendly name (e.g. `Apply form`); `Abuse type` is filled only on abuse records (`same_ip_multiple`, `bot_user_agent`, ...). Empty values are not sent. They are sent on real leads AND abuse records. If Heffl rejects the keys (a column is missing or misspelled) the lead is created without them and the same details go into the linked task, so nothing is lost; the log line `heffl_custom_fields_rejected` tells you.
- Task text: submission time is shown in India time (`4 Nov 2026, 2:15 AM IST`; logs keep ISO UTC). Friendly form labels replace internal names in task titles and text (`Follow up: <name> (<situation>, via <friendly label>)`): `dm_by_adsmentor_apply` Apply form, `magnet_syllabus` Free guide: 12-week syllabus, `magnet_checklist` Free guide: 5-question course checklist, `magnet_ad_account` Free guide: ad account ownership checklist, `magnet_brochure` Brochure download, source `magnet-rtcros-prompt-guide` Free guide: RTCROS prompt guide, `magnet-meta-mcp-cli-sop` Free guide: Meta Ads MCP and CLI SOP; `magnet-ai-announcement-checklist` Free guide: AI announcement checklist; unknown names show the raw value. Add new forms to `FORM_LABELS` / `SOURCE_LABELS` in `api/lead.js`.
- Privacy: `privacy-policy.html` states the IP/location capture, the tracking and analytics tools (Clarity, Google Analytics, Tag Manager) and that form details are stored in Heffl. Update it whenever what is collected or who receives it changes.
- Attribution (UTM / campaign data), first-party, no form markup change: `wp-content/plugins/elementor/assets/js/aim-track.js` (loaded on every page by `scripts/inject-gtm.js`; the injector sets the `?ver=` string, currently `1.1.0`, and rewrites older ones in existing pages, so bump `TRACK_VER` there whenever aim-track.js changes). On every page load it reads `utm_source/medium/campaign/term/content`, `gclid`, `fbclid`, `msclkid` from the URL (each max 120 chars, control characters and angle brackets stripped), the referrer host (not aiinmarketing.in / www) and the landing path. FIRST touch: `localStorage['aim_attr_first']`, written once with a timestamp, expires after 30 days. LAST touch: `sessionStorage['aim_attr_last']`, overwritten whenever the page has any utm or click id, otherwise kept. Every storage access is in try/catch; with storage blocked the current page's data is still used. A capture-phase `submit` listener (forms whose action contains `admin-ajax.php` or whose class contains `elementor-form` / `aim-magnet-form`) adds hidden inputs `form_fields[utm_source|utm_medium|utm_campaign|utm_term|utm_content|click_id|referrer_host|landing_path|attribution]` before the page's own handlers build the FormData. Rule: last touch wins for the campaign fields when it carries utm/click data, else first touch; `click_id` is `gclid:XXX` (else fbclid, else msclkid); `attribution` is `last`, `first` or `direct`; referrer host and landing path come from the first touch. A dataLayer event `attribution_set` (source/medium/campaign only, no personal data) is pushed once per session when any UTM exists.
- `api/lead.js` accepts those fields (capped, sanitised) and falls back to `utm_*`/click ids in the `referer` URL when they are missing. Real leads: the follow-up task text has the line `Campaign / UTM: source / medium / campaign / term / content; click id present: yes/no; referrer: <host>; first landing: <path>; attribution: first|last|direct` (same text in `cf_campaign_utm` in custom-fields mode). The click id value is never sent to Heffl and logs show only type + first 6 characters (`gclid:ABCDEF`).
- Abuse records carry IP, geo and campaign data in the lead `title` (the v1 create-lead call has no notes field; custom fields would only work after the owner creates them, and the full context goes into the linked abuse task described above; the owner first asked for no tasks, then complained the IP and form details were missing). Format, empty parts omitted, cut from the right at 190 characters (Heffl documents no maximum) so the type and IP always survive: `ABUSE: <type> | IP <ip> | <CC>, <region>, <city> | src=<utm_source> med=<utm_medium> cmp=<utm_campaign> | ref=<referrer host> | term=<utm_term> content=<utm_content> click=<gclid|fbclid|msclkid> | land=<first landing path>`. Example: `ABUSE: bot_user_agent | IP 203.0.113.50 | IN, KL, Kochi | src=google med=cpc cmp=spring | ref=www.google.com | term=ai course | land=/blog/post`. If the duplicate-contact retry is used the title is `ABUSE: <type> | IP <ip> | <email> <mobile> | ...`. IP and geo are logged for every abuse type (`abuse_flagged`, also with campaign data) and for rejected requests (`request_rejected`, reason `bad_origin` or `invalid_input`), even when the request carries no UTM (bots usually run no JavaScript).
- Same IP, different details (spam): per warm instance, the 2nd and later different email+phone pair from one IP within 10 minutes (the first person is a normal lead) (until the 5-per-IP rate limit answers 429) gets the normal success message and is stored as `ABUSE: same_ip_multiple | IP <ip> | ...` in `Unqualified` with the name, mobile and email they typed (no New lead; the abuse task carries IP and form details). Best effort: the memory is per warm serverless instance, so two requests served by different instances are not linked. Constant: `IP_IDENTITY_MAX` in `api/lead.js`. Mobile carriers and campuses can share an IP, so review `Unqualified` now and then and move genuine people to New.
- NO DATA IS LOST (owner rule): every submission that carries a name, phone or email is kept. Abuse of any type (`bad_origin`, `rate_limit`, `repeat_within_60s`, `bot_user_agent`, `same_ip_multiple`) becomes an `Unqualified` lead with the typed contact details. Details that fail validation (`invalid_input`, also with a bad origin) become an `Unqualified` lead with the typed name and `phone=<typed> email=<typed>` in the title (no contact fields, Heffl would reject them). If Heffl cannot take an abuse record (no key, 20/hour cap, `Unqualified` stage missing, Heffl error) the full record is logged as `lead_crm_failed` (Vercel runtime logs) and posted to `LEAD_WEBHOOK_URL` if set. A submission with nothing typed creates nothing. The visitor's response never changes (400 for bad origin / invalid input, 429 for rate limit, success otherwise).
- Tests: `node tools/test-lead.js` (function, offline) and `node tools/test-attribution.js [baseUrl]` (Playwright; serve the repo with `nohup python3 -m http.server 8777 &`; the form POST is always intercepted and answered by a mock, so it is safe against the live site too).
- Run `node tools/test-lead.js` after any change to `api/lead.js`, and `node tools/test-attribution.js` after any change to `aim-track.js` or the forms.

Then delete the test lead (and its task) in Heffl. Heffl has "Allow duplicate leads" off, so repeat tests need a different email and phone.

## Parallel sessions (content, design, security): nothing may overwrite anything

Several Claude sessions work on this repository at the same time (content desk, design, security / lead capture). The owner's rule: security and lead-capture work (`api/lead.js`, IP and abuse rules, attribution in `aim-track.js`, privacy sentence, GTM) has PRIORITY and must survive every other update, and every other update must survive too.

Every session, before every push (use `bash scripts/publish.sh`, which does all of this; the build guard `scripts/guard.js` now enforces it on Vercel):
1. Commit your own work, then `git fetch origin main` and `git rebase origin/main` (or `git pull --rebase origin main`). Never `git push --force` / `--force-with-lease` to main, never `git reset --hard origin/main` over your own unpushed work, never overwrite a file wholesale with an older copy (copy-pasting a whole page from an old checkout drops newer changes: edit in place).
2. Resolve conflicts by keeping BOTH sides. For `api/lead.js`, `aim-track.js`, `scripts/inject-gtm.js`, `privacy-policy.html`, `CLAUDE.md`, `README.md`, `tools/test-lead.js` the protected (security) version wins any real conflict.
3. Run `node scripts/inject-gtm.js` and `node tools/verify-protected.js`. If it reports a problem, a protected change is missing: restore it from git history (`git log -p -- <file>`), re-apply your change on top, run it again, then push.
4. After pushing, `git fetch` again and re-run `node tools/verify-protected.js` against `origin/main`; if the content you pushed removed a protected change, fix it immediately in a new commit (never by force).
5. New blog posts and pages need nothing special for the security features: the Vercel build injects GTM and `aim-track.js` at the current version, and the lead endpoint is not part of the page. Do not copy old inline form scripts into new pages.
